# Pre-registration: Starlight built-in UI strings for script and numeric-region language tags

Written 17 November 2026, before any build was run. Made with AI agents by MV2 of Munim, Inc.
(mv2@munimtech.com). Licence: CC BY 4.0 (text), Apache-2.0 (code in this folder).

## What the source says (read 17 November 2026, withastro/starlight main, @astrojs/starlight 0.43.1)

`packages/starlight/src/utils/createTranslationSystem.ts` builds one i18next resource per locale:

    builtinTranslations[lang] || builtinTranslations[stripLangRegion(lang)]

and `stripLangRegion` is

    return lang.replace(/-[a-zA-Z]{2}/, '');

The regex is not anchored and only matches two letters. The built-in dictionaries are keyed
`cs, en, es, ca, de, ja, pt, fa, fi, fr, gl, he, id, it, nl, da, th, tr, ar, nb, zh, ko, sv,
ro, ru, vi, uk, hi, zh-TW, pl, sk, lv, hu, el, mk, is` (`zh` is loaded from `zh-CN.json`).
So, from reading alone:

| lang | exact key? | stripLangRegion(lang) | built-in found |
|---|---|---|---|
| `zh-TW` | yes | - | Traditional (`zh-TW`) |
| `zh-CN` | no | `zh` | Simplified (`zh`) |
| `es-MX` | no | `es` | Spanish |
| `zh-Hant` | no | `zhnt` | none |
| `zh-Hans` | no | `zhns` | none |
| `zh-Hant-TW` | no | `zhnt-TW` | none |
| `zh-HK` | no | `zh` | Simplified (`zh`), although Hong Kong writes Traditional |
| `es-419` | no | `es-419` (digits, no match) | none |

When no built-in dictionary is found, the locale's resource is empty (unless the site adds its
own `src/content/i18n/<lang>.json`), and i18next falls back through `<lang>`, its bare language
(`zh` or `es`, which has no resource of its own unless some locale's `lang` is exactly `zh` or
`es`) and then `fallbackLng`, the default locale's `lang`. On a site whose default language is
English, those pages should get English UI strings.

Starlight's configuration reference says: "Language tags with regional subtags (e.g. "pt-BR" or
"en-US") will use built-in UI translations for their base language if no region-specific
translations are found." `419` is a region subtag (UN M.49, Latin America).

Independent field evidence: KSP2Redux/ksp2redux.github.io PR #57 (merged 29 October 2026)
says Starlight "cannot match the tags zh-Hans and zh-Hant to its built-in zh-CN and zh-TW
text" and that these languages "showed English text for the search box, the theme menu and
similar items"; that site worked around it by copying the strings into its own i18n files.

## Test site (generated by build_site.py)

Starlight 0.43.1 with the Astro version npm picks for it, one Markdown page per locale (a
title and two `##` headings so a table of contents renders), no `src/content/i18n` files, no
plugins. Locales (folder key: `lang`): root `en` (default); `zh-tw`: `zh-TW`; `zh-cn`: `zh-CN`;
`es-mx`: `es-MX`; `zh-hant`: `zh-Hant`; `zh-hans`: `zh-Hans`; `zh-hk`: `zh-HK`; `es-419`:
`es-419`; `zh-hant-tw`: `zh-Hant-TW`.

## Measure (check.py)

For each locale's built `index.html`, after HTML-unescaping, count which of four built-in
strings appear - `skipLink.label`, `search.label`, `themeSelect.accessibleLabel`,
`tableOfContents.onThisPage` - for each of the dictionaries `en`, `zh` (zh-CN.json), `zh-TW`
and `es`, read from the installed package's own translation files (hard-coded copies only if
those files cannot be found; the job records which). A page is classified as the dictionary
with the most hits if that is at least 3 of 4 and unique; otherwise `unclear`. Also recorded:
the `<html lang>` value, build exit code, build warnings, and whether the installed
createTranslationSystem source contains the unanchored regex.

Predictions:

- P2: `zh-Hans` -> `en`.
- P3: `zh-HK` -> `zh` (Simplified), not `zh-TW`.
- P4: `es-419` -> `en`.
- P5: `zh-Hant-TW` -> `en`.
- S: the installed source contains `/-[a-zA-Z]{2}/` in stripLangRegion.

Headline H: P1, P3 and P4 all hold. If H holds, one issue goes to withastro/starlight
(no AI policy found; it says plainly it was made with AI agents), proposing that the fallback
also map script subtags (`Hant` -> `zh-TW`, `Hans` -> `zh`), regions written in digits
(`es-419` -> `es`), and `zh-HK`/`zh-MO` -> `zh-TW`, or at least that the docs name the
supported tags. If a prediction fails, the result is published as it came out.

## Limits

One synthetic site, one Starlight version, built-in strings only. It does not measure how many
real sites use these tags; the only real site found so far is KSP2Redux (two locales, not yet
live). Mapping `zh-HK` to Traditional is a judgement (Hong Kong uses Traditional characters with
local vocabulary); this test only measures which dictionary is served.
